# Security Lens

> 사진 속 개인정보와 숨겨진 메타데이터를 탐지하고, 공유하기 전에 보호할 수 있도록 돕는 이미지 개인정보 분석 서비스

**Java 17 · Spring Boot 4.1.1 · Tesseract OCR · OpenAI API · Docker · Railway · Vanilla JavaScript**

## Live Demo

https://securitylens.up.railway.app

## Engineering Highlights

- **Fast Scan / Deep Analysis:** OCR·규칙 기반 개인정보 탐지·EXIF 분석 결과를 먼저 제공하고, AI 문맥 및 문서 분석으로 결과를 보완
- **OCR Concurrency Control:** Railway 환경의 k6 부하 테스트에서 OCR 동시 실행에 따른 메모리 문제를 확인하고 Semaphore를 적용해 동시 OCR 작업을 최대 2개로 제한
- **Image Protection:** 탐지 영역을 브라우저 Canvas에서 마스킹하고 이미지를 재생성하여 기존 메타데이터 제거
- **Deployment:** Docker 기반 Linux 환경에 Tesseract OCR 및 Spring Boot 애플리케이션 배포

## Architecture at a Glance

```text
Image Upload
    ↓
Spring Boot API
    ├── Fast Scan: OCR + Rule-based PII Detection + EXIF
    └── Deep Analysis: AI Context + Document Vision
    ↓
Risk Score + Detected Items + Bounding Boxes
    ↓
Browser Canvas: Selected PII Masking + Image Re-encoding
    ↓
Protected Image
```

**Project Context:** Wanted AI Championship 2026을 계기로 개발한 개인 MVP로, 이미지 개인정보 탐지부터 보호 이미지 생성까지의 흐름을 구현했습니다.

## 왜 만들었나

인터넷을 사용하다 보면 내가 생각하는 것보다 훨씬 많은 정보가 남는다는 느낌을 받을 때가 있습니다.

IP 주소부터 접속 기록, 사용 환경, 그리고 우리가 매일 사용하는 여러 서비스까지
생각보다 많은 정보가 수집되고 분석될 수 있습니다.

그중에서 가장 가까우면서도 직접 확인해볼 수 있는 소재가 사진이라고 생각했습니다.

사진은 화면에 보이는 것만 보면 그냥 한 장의 이미지입니다.
하지만 파일 안에는 촬영 위치, 촬영 시간, 사용한 기기처럼
눈으로는 보이지 않는 정보가 함께 들어 있을 수 있습니다.

처음에는 사진을 새롭게 생성하거나 픽셀을 바꾸는 것보다,
이미 사진 안에 존재하는 데이터를 직접 읽어보는 것에서 시작했습니다.

그리고 실제로 확인해보니 숨겨진 메타데이터뿐 아니라
사진 화면 안에도 이름, 전화번호, 주소처럼
공유 전에 한 번 더 확인해야 할 정보가 있을 수 있었습니다.

그래서 사진을 올리면
눈에 보이는 개인정보와 눈에 보이지 않는 정보를 함께 확인하고,
공유하기 전에 필요한 부분을 보호할 수 있는 도구를 만들어보고 싶었습니다.

그렇게 Security Lens를 시작했습니다.

## Security Lens는 어떻게 해결하나

Security Lens는 사진 한 장을 기준으로
눈에 보이는 정보와 눈에 보이지 않는 정보를 순서대로 확인합니다.

사진을 업로드하면 먼저 OCR과 개인정보 탐지를 통해
이름, 전화번호, 이메일, 주소 등 화면에 노출된 정보를 찾습니다.

동시에 사진 파일 안에 남아 있는 메타데이터를 확인해
촬영 위치, 촬영 시간, 사용 기기와 같은 숨겨진 정보가 있는지도 살펴봅니다.

이후 탐지된 결과와 사진의 맥락을 함께 분석해
사용자가 한눈에 확인할 수 있도록 개인정보 위험도와 설명을 제공합니다.

```text
사진 업로드
    ↓
화면 속 개인정보 탐지
    ↓
숨겨진 메타데이터 분석
    ↓
AI 기반 맥락 분석
    ↓
개인정보 위험도 확인
    ↓
노출 정보 보호
    ↓
보호된 이미지 저장
```

단순히 위험하다고 알려주는 것에서 끝내지 않고,
사용자가 바로 공유할 수 있는 이미지까지 만드는 것을 목표로 했습니다.

화면에서 탐지된 개인정보는 필요한 항목을 선택해 가릴 수 있고,
보호 이미지를 새로 생성하는 과정에서 기존 사진의 메타데이터도 함께 제거합니다.

## 주요 기능

### 눈에 보이는 개인정보 탐지

OCR을 통해 이미지 안의 텍스트를 읽고
이름, 전화번호, 이메일, 주소 등 개인정보로 판단되는 항목을 탐지합니다.

### 숨겨진 메타데이터 확인

사진 파일에 포함된 GPS 위치 정보, 촬영 시간,
촬영 기기 정보를 확인합니다.

### 개인정보 위험도 분석

탐지된 개인정보와 메타데이터를 바탕으로
사진의 개인정보 노출 위험도를 점수와 단계로 보여줍니다.

### AI 기반 문맥·문서 분석

OCR 결과의 문맥을 이용해 사람 이름과 주소를 판별하고,
문서 구조가 중요한 경우에는 Vision 분석으로
개인정보 영역과 문서 맥락을 보완합니다.

### 개인정보 영역 표시

탐지된 개인정보의 위치를 이미지 위에 표시해
어떤 부분이 위험 요소인지 직접 확인할 수 있습니다.

### 보호 이미지 생성

사용자가 보호할 항목을 선택하면 해당 영역을 마스킹하고,
이미지를 다시 생성하면서 기존 메타데이터도 함께 제거합니다.

### 한국어 / 영어 지원

브라우저 언어에 따라 한국어와 영어 UI를 제공합니다.

## AI는 어디에 사용했나

Security Lens는 모든 개인정보 탐지를 AI에 맡기지 않습니다.

전화번호, 이메일, 주민등록번호처럼 형식이 비교적 명확한 정보는
OCR 결과와 규칙 기반 탐지를 먼저 사용하고,
GPS, 촬영 시간, 기기 정보는 이미지 파일의 메타데이터에서 직접 확인합니다.

AI는 규칙만으로 판단하기 어려운 영역을 보완합니다.

### OCR Context Analysis

OCR이 읽은 각 단어에 ID를 부여한 뒤,
AI가 문맥을 보고 실제 사람 이름과 구체적인 주소에 해당하는
Word ID를 선택하도록 구성했습니다.

AI가 개인정보 문자열을 새로 만들어내는 대신,
실제 OCR 결과 안에서 근거가 되는 단어를 선택하게 함으로써
탐지 결과를 원본 이미지의 위치와 연결합니다.

### Document Vision

OCR 품질이 낮거나 운전면허증, 여권, 민감 문서처럼
문서 구조 자체가 중요한 경우에는 이미지 기반 분석을 추가로 수행합니다.

이 단계에서는 문서 종류와 함께
이름, 주민등록번호, 운전면허번호, 여권번호,
생년월일, 주소 등의 실제 위치를 Bounding Box로 찾습니다.

### Fast Scan + Deep Analysis

사용자가 AI 분석이 모두 끝날 때까지 기다리지 않도록
분석을 Fast Scan과 Deep Analysis로 나누었습니다.

Fast Scan에서는 OCR, 규칙 기반 개인정보 탐지,
EXIF 메타데이터 분석을 먼저 수행해 빠르게 결과를 보여주고,

Deep Analysis에서는 OCR 문맥 분석과 Document Vision으로
누락된 개인정보와 문서 맥락을 보완합니다.

AI가 잘하는 의미·문맥 판단과
일반 코드가 더 안정적인 정형 데이터 처리를 분리한 것이
Security Lens의 핵심 설계 중 하나입니다.

### 개발 과정에서의 AI 활용

이번 프로젝트를 개발하는 과정에서도 AI를 적극적으로 활용했습니다.

ChatGPT는 문제 정의, 기능 설계, 구현 방향 검토,
디버깅과 테스트 시나리오를 함께 정리하는 데 사용했습니다.

Claude는 실제 코드 구현과 리팩터링,
기존 코드 검토를 보조하는 도구로 활용했습니다.

AI가 제안한 코드를 그대로 합치는 방식으로 개발하지 않았습니다.
실제 이미지에서 예상과 다른 결과가 나오면 로그와 코드 흐름을 다시 확인했고,
수정 후에는 diff와 테스트 결과를 확인한 뒤 배포했습니다.

배포 이후에도 실제 이미지 테스트와 k6 부하 테스트를 진행했고, 
OCR 동시 처리에서 메모리 문제가 발생했을 때는 로그와 서버 지표를 바탕으로 원인을 좁혀 Semaphore를 적용했습니다.

이번 프로젝트에서 AI는 코드를 대신 만들어주는 도구라기보다, 
함께 가설을 세우고 구현하고 검토하는 개발 파트너에 가까웠습니다. 

최종적으로 어떤 코드를 사용할지와 결과가 제대로 동작하는지 확인하는 것은 제가 책임져야 할 부분이라고 생각했습니다.

## 기술 스택

이번 프로젝트에서는 새로운 기술을 많이 사용하는 것보다,
제가 익숙한 Java와 Spring Boot를 중심으로
이미지 분석에 필요한 기술을 하나씩 결합하는 방향으로 구성했습니다.

| 영역 | 기술 | 역할 |
| --- | --- | --- |
| Backend | Java 17, Spring Boot | 이미지 분석 API와 전체 서비스 로직 |
| Build | Gradle | 빌드 및 의존성 관리 |
| OCR | Tesseract OCR, Tess4J | 이미지 안의 텍스트 인식 |
| Privacy Analysis | 개인정보 탐지 로직, EXIF 메타데이터 분석 | 화면에 보이는 개인정보와 숨겨진 메타데이터 탐지 |
| AI | OpenAI API, gpt-5.6-terra | OCR 문맥 기반 개인정보 판별 및 구조화 문서의 개인정보 영역 탐지 |
| Frontend | HTML, CSS, Vanilla JavaScript | 이미지 업로드, 분석 결과 표시, 개인정보 영역 표시 및 보호 |
| Image Protection | Canvas API | 개인정보 영역 마스킹 및 메타데이터가 제거된 이미지 재생성 |
| Deployment | Docker, Railway | Linux 환경 컨테이너 빌드 및 서비스 배포 |
| Version Control | Git, GitHub | 소스 관리 및 배포 연동 |

### 왜 이렇게 구성했나

Security Lens는 한 장의 이미지를 빠르게 분석하고 결과를 보여주는 서비스이기 때문에
MVP 단계에서는 별도의 프론트엔드 프레임워크를 추가하지 않았습니다.

Frontend는 HTML, CSS, JavaScript만으로 구성하고,
분석과 개인정보 처리 로직은 Spring Boot Backend에 집중했습니다.

OCR처럼 운영체제의 영향을 받는 기능은
로컬 Windows 환경에서만 동작하는 것에 그치지 않도록
Docker 기반 Linux 환경에서도 실제로 실행해보며 맞춰 나갔습니다.

AI 역시 모든 기능을 대신하도록 만들기보다,
일반 코드로 안정적으로 처리할 수 있는 정형 정보는 코드가 담당하고,
사람 이름이나 주소처럼 문맥이 필요한 개인정보 판별과
문서 구조를 이용한 개인정보 영역 탐지를 AI가 보완하도록 구성했습니다.

## 시스템 구조

Security Lens는 하나의 Spring Boot 애플리케이션 안에서
Frontend와 이미지 분석 API를 함께 제공하는 구조로 만들었습니다.

MVP 단계에서는 서비스를 여러 개로 나누기보다
분석 흐름을 단순하게 유지하고 실제 동작하는 서비스까지 완성하는 데 집중했습니다.

```text
사용자 브라우저
      │
      │ 이미지 업로드
      ▼
Spring Boot
      │
      ├─ 이미지 유효성 검사
      │
      ├─ OCR
      │    └─ 이미지 속 텍스트 추출
      │
      ├─ 개인정보 탐지
      │    └─ 이름 / 전화번호 / 이메일 / 주소 등
      │
      ├─ 메타데이터 분석
      │    └─ GPS / 촬영 시간 / 촬영 기기
      │
      ├─ Risk 분석
      │    └─ 탐지 결과를 기반으로 위험도 계산
      │
      └─ AI 심화 분석
            ├─ OCR 문맥 기반 개인정보 판별
            └─ Document Vision 기반 문서·개인정보 영역 보완
      │
      ▼
분석 결과 반환
      │
      ▼
Frontend
      │
      ├─ 위험 점수 및 탐지 결과 표시
      ├─ 개인정보 위치 표시
      └─ 보호할 영역 선택
      │
      ▼
Canvas API
      │
      ├─ 개인정보 영역 마스킹
      └─ 이미지 재생성 및 메타데이터 제거
      │
      ▼
보호된 이미지
```

### Fast Scan과 Deep Analysis

사용자가 결과를 보기 위해 AI 분석이 모두 끝날 때까지 기다리지 않도록
분석 과정을 두 단계로 나누었습니다.

Fast Scan에서는 OCR, 개인정보 탐지, 메타데이터 분석 등
먼저 확인할 수 있는 결과를 빠르게 반환합니다.

그 결과를 화면에 먼저 보여준 뒤,
Deep Analysis를 통해 AI 기반 심화 분석을 수행하고
완료된 결과로 화면을 갱신합니다.

이 방식으로 AI 분석 시간이 있더라도
사용자가 빈 화면에서 기다리는 시간을 줄이고자 했습니다.

## 실행 방법

### 서비스 체험

Security Lens는 별도의 회원가입이나 로그인 없이 사용할 수 있습니다.

https://securitylens.up.railway.app

JPG, JPEG, PNG 이미지를 한 장씩 업로드해 분석할 수 있습니다.

### 로컬 실행

소스코드는 공개되어 있으며, 아래 명령어로 내려받을 수 있습니다.

```bash
git clone https://github.com/nocklock-h/security-lens.git
cd security-lens
```

Deep Analysis를 사용하려면 `OPENAI_API_KEY` 환경변수 설정이 필요합니다.

### 요구 환경

- Java 17
- Gradle Wrapper
- Tesseract OCR
- AI 심화 분석을 위한 외부 LLM API
- JPG, JPEG, PNG 이미지

Windows에서는 다음 명령어로 실행할 수 있습니다.

```bash
gradlew.bat bootRun
```

macOS 또는 Linux에서는 다음과 같이 실행합니다.

```bash
./gradlew bootRun
```

기본 로컬 포트는 8081입니다.

```text
http://localhost:8081
```

브라우저에서 위 주소로 접속하면
별도의 로그인이나 회원가입 없이 이미지를 분석할 수 있습니다.

### AI API 설정

Security Lens의 Deep Analysis에서는 OpenAI API를 사용합니다.

현재 프로젝트에서는 일반 심화 분석과 이미지 맥락 분석에
`gpt-5.6-terra` 모델을 사용하도록 구성했습니다.

```text
AI Provider  : OpenAI API
Model        : gpt-5.6-terra
Vision Model : gpt-5.6-terra
```

API Key는 소스코드나 설정 파일에 직접 저장하지 않고
`OPENAI_API_KEY` 환경변수를 통해 주입합니다.

예를 들어 Windows PowerShell에서는 다음과 같이 설정할 수 있습니다.

```powershell
$env:OPENAI_API_KEY="YOUR_API_KEY"
```

macOS 또는 Linux에서는 다음과 같이 설정할 수 있습니다.

```bash
export OPENAI_API_KEY="YOUR_API_KEY"
```

실제 API Key는 GitHub 저장소나 README에 기록하지 않습니다.

배포 환경인 Railway에서도 동일하게
`OPENAI_API_KEY`를 Environment Variable로 등록해 사용합니다.

### 성능 및 부하 테스트

Railway 실제 배포 환경을 대상으로 k6 부하 테스트를 진행했습니다.

초기 테스트에서는 여러 OCR 요청이 동시에 실행되며
Tesseract 전처리 이미지와 native 처리 메모리가 함께 증가해
Java Heap 부족이 발생하는 상황을 확인했습니다.

이를 완화하기 위해 OcrService에 Semaphore를 적용해
동시에 실행되는 OCR 작업을 최대 2개로 제한했습니다.

최종 배포 버전에서는 약 1.9MB의 복잡한 테스트 이미지를
5명이 동시에 Fast Scan하는 시나리오를 다시 검증했습니다.

- 요청: 5
- HTTP 200: 5 / 5
- 실패율: 0%
- 평균 응답 시간: 약 39.7초
- p95: 약 55초

모든 요청은 정상 처리되었지만,
동시 요청이 증가할수록 Tesseract OCR의 CPU 경합으로
응답 시간이 크게 증가하는 것을 확인했습니다.

현재 Semaphore는 처리량을 높이기 위한 최종 해결책이 아니라,
제한된 MVP 서버 자원에서 과도한 OCR 동시 실행으로
서비스 전체가 중단되는 것을 막기 위한 안전장치입니다.

향후에는 bounded worker queue, backpressure,
OCR worker 분리 및 수평 확장을 통해 개선할 계획입니다.

#### 향후 성능 개선 방향

현재 테스트를 통해 단순히 서버 사양을 높이는 것보다
OCR 작업을 별도의 제한된 실행 자원으로 관리하는 것이 중요하다는 점을 확인했습니다.

향후에는 다음 항목을 순서대로 개선할 계획입니다.

- 이미지 해상도와 예상 픽셀 수를 기준으로 전처리 크기를 더 세밀하게 제한
- OCR 전용 bounded worker pool 또는 작업 큐를 적용해 request thread와 무거운 OCR 작업을 분리
- 서버가 감당할 수 있는 범위를 초과한 요청에 대한 backpressure와 timeout 정책 추가
- CPU, JVM Heap, GC, OCR 처리 시간에 대한 모니터링과 알림 추가
- 다양한 해상도와 문서 유형을 포함한 고정 벤치마크 데이터셋 구성
- 평균 응답 시간뿐 아니라 p95, p99, 오류율, 처리량을 함께 지속 측정
- 트래픽이 증가할 경우 OCR worker 분리 또는 수평 확장 검토

이번 테스트는 같은 합성 이미지를 반복해 측정한 결과이므로
모든 실제 이미지의 성능을 대표한다고 보지는 않습니다.

MVP 이후에는 실제 사용 패턴에 가까운 이미지 크기와 요청 분포를 기준으로
부하 테스트 시나리오를 다시 설계하고,
동시성 제한 값을 서버 자원에 맞게 조정할 계획입니다.


### Docker

실제 배포 환경에서는 Docker를 사용합니다.

OCR은 운영체제의 native library 영향을 받기 때문에
로컬 Windows 환경에서만 동작하는 것에 그치지 않도록
Tesseract와 Leptonica가 포함된 Linux 컨테이너 환경으로 구성했습니다.

```bash
docker build -t security-lens .
docker run -p 8080:8080 security-lens
```

Docker를 이용하면 Tesseract OCR과 Spring Boot 애플리케이션을 Linux 컨테이너 환경에서 실행할 수 있습니다.

먼저 이미지를 빌드합니다.

```bash
docker build -t security-lens .
```

macOS 또는 Linux에서는 `OPENAI_API_KEY` 환경변수를 설정한 뒤 실행합니다.

```bash
docker run --rm -p 8080:8080 \
  -e OPENAI_API_KEY="$OPENAI_API_KEY" \
  security-lens
```

Windows PowerShell에서는 다음과 같이 실행합니다.

```powershell
docker run --rm -p 8080:8080 `
  -e OPENAI_API_KEY=$env:OPENAI_API_KEY `
  security-lens
```

실행 후 다음 주소로 접속할 수 있습니다.

http://localhost:8080

API Key는 Docker 이미지에 포함하지 않고 실행 환경에서 주입합니다.

## API

Security Lens의 Frontend는 Spring Boot API를 통해
이미지 분석과 화면에 필요한 데이터를 요청합니다.

### Fast Scan

```http
POST /api/v1/images/analyze/fast
```

이미지를 전달하면 OCR, 개인정보 탐지, 메타데이터 분석 등
먼저 확인할 수 있는 결과를 반환합니다.

분석 결과를 최대한 빠르게 사용자에게 보여주기 위한 API입니다.

### Deep Analysis

```http
POST /api/v1/images/analyze/deep
```

OpenAI API를 이용한 심화 분석을 수행합니다.

Fast Scan 결과가 먼저 화면에 표시되고,
Deep Analysis가 끝나면 AI 분석 결과와 설명을 화면에 반영합니다.

### UI Messages

```http
GET /api/v1/ui/messages?lang=ko
```

브라우저 언어에 맞는 UI 문구를 가져옵니다.

현재 한국어와 영어를 지원합니다.

### 분석 결과

분석 결과에는 개인정보 위험 점수와 단계,
탐지된 개인정보, 위치 정보, 메타데이터,
AI 분석 결과와 요약 설명 등이 포함됩니다.

Frontend는 이 결과를 이용해
탐지된 개인정보의 위치를 이미지 위에 표시하고,
사용자가 보호할 항목을 선택할 수 있도록 구성했습니다.

## 개인정보와 보안

Security Lens 자체가 개인정보를 다루는 서비스인 만큼
기능을 구현할 때도 개인정보가 불필요하게 노출되지 않도록 신경 썼습니다.

### API Key 관리

OpenAI API Key는 소스코드에 직접 작성하지 않고
`OPENAI_API_KEY` 환경변수를 통해 주입합니다.

로컬 환경과 Railway 배포 환경에서도
실제 Key 값은 코드와 분리해서 관리합니다.

### 개인정보 보호 방식

탐지된 개인정보는 이미지 위에서 위치를 확인할 수 있고,
사용자가 보호할 항목을 선택할 수 있습니다.

보호를 실행하면 선택된 개인정보 영역을
불투명한 마스크로 가린 새로운 이미지를 생성합니다.

블러(Blur) 처리보다 원본 문자가 남을 가능성을 줄이기 위해
MVP에서는 불투명 마스킹 방식을 사용했습니다.

### 메타데이터 제거

개인정보 영역만 가리고 끝내지 않습니다.

보호 이미지를 생성할 때 브라우저의 Canvas를 이용해
JPEG 또는 PNG 이미지를 새로 생성합니다.

이 과정에서 원본 이미지에 포함되어 있던
GPS 위치, 촬영 시간, 촬영 기기 등의 EXIF 메타데이터가
새로운 이미지에 다시 포함되지 않도록 했습니다.

즉 Security Lens의 보호 과정은

```text
화면에 보이는 개인정보 마스킹
+
사진 속 숨겨진 메타데이터 제거
```

두 가지를 함께 처리하는 것을 목표로 합니다.

### 사용자가 최종적으로 확인

개인정보 탐지 결과를 기준으로 자동으로 원본 이미지를 변경하지 않고,
어떤 정보가 탐지되었는지 먼저 보여준 뒤
사용자가 보호할 항목을 확인할 수 있도록 구성했습니다.

AI 분석 결과 역시 최종 판단 자체보다는
사용자가 사진을 공유하기 전에 위험 요소를 확인하기 위한 정보로 제공합니다.

## 현재 한계와 개선하고 싶은 부분

이번 버전은 Wanted AI Championship 제출을 목표로 만든 MVP이기 때문에
기능을 넓히는 것보다 핵심 흐름을 실제로 동작시키는 데 집중했습니다.

### OCR 정확도

현재 개인정보 탐지는 OCR 결과를 기반으로 하기 때문에
사진의 해상도, 글자 크기, 배경, 촬영 각도에 따라
일부 텍스트를 정확하게 인식하지 못할 수 있습니다.

앞으로는 다양한 이미지 환경에서 테스트 데이터를 늘리고,
OCR 결과 보정과 개인정보 탐지 정확도를 개선하고 싶습니다.

### 지원 이미지 범위

현재는 JPG, JPEG, PNG 이미지를 지원하며
한 번에 한 장의 이미지를 분석하는 방식으로 구성했습니다.

향후에는 여러 이미지를 한 번에 검사하거나
더 다양한 이미지 형식을 지원하는 방향도 고려하고 있습니다.

### 모바일 브라우저 저장 방식

일반 브라우저에서는 보호된 이미지를 저장할 수 있지만,
일부 인앱 브라우저에서는 브라우저 자체의 파일 저장 정책 때문에
동일한 방식으로 동작하지 않을 수 있습니다.

현재 Android 카카오톡 인앱 브라우저에서는
다른 브라우저에서 열도록 안내하고 있습니다.

향후에는 모바일 환경에서도 더 일관된 방식으로
보호 이미지를 저장할 수 있도록 개선할 계획입니다.

### AI 분석 의존성

Deep Analysis는 외부 OpenAI API를 사용하기 때문에
API 응답 시간이나 외부 서비스 상태의 영향을 받을 수 있습니다.

이 경우에도 먼저 완료된 Fast Scan 결과는 유지하도록 구성했습니다.

앞으로는 AI 분석이 실패하거나 지연되는 상황에서도
사용자가 서비스를 계속 사용할 수 있도록 예외 처리를 더 보완하고 싶습니다.

## 앞으로

이번 프로젝트를 만들면서 Security Lens를
단순히 사진 한 장을 검사하는 독립적인 서비스로만 볼 필요는 없다고 생각했습니다.

개인정보 문제는 사진을 분석하는 순간보다
결국 그 사진을 다른 사람에게 보내거나 외부에 공개하는 순간에 발생하기 때문입니다.

그래서 앞으로는 기능을 계속 넓히기보다
현재의 개인정보 탐지와 보호 기능을 더 깊게 발전시키는 방향을 생각하고 있습니다.

### 개인용 도구에서 B2B로

기업에서는 메일, 메신저, 게시판, 고객 응대 시스템 등
다양한 경로를 통해 이미지와 문서가 외부로 전달됩니다.

이 과정에서 직원이 의도하지 않게
전화번호, 주소, 문서 정보나 위치 메타데이터가 포함된 파일을
외부로 전송할 수도 있습니다.

Security Lens의 분석 기능을 API 형태로 발전시키면
파일이 외부로 전달되기 전에 개인정보 노출 가능성을 확인하고
사용자에게 경고하거나 보호 처리를 제안하는 방식으로 확장할 수 있다고 생각합니다.

### 사용하는 서비스 안에서 동작하는 Security Lens

개인정보 보호를 위해 매번 별도의 사이트에 접속하고
파일을 직접 업로드하는 방식은 실제 사용 환경에서는 번거로울 수 있습니다.

그래서 장기적으로는 Security Lens 자체를 하나의 목적지로 만드는 것보다
사용자가 이미 사용하고 있는 서비스의 흐름 안에서 동작하게 만들고 싶습니다.

예를 들어 메일에 이미지를 첨부하거나
메신저나 웹 서비스에 사진을 올리는 순간

```text
이미지 첨부
    ↓
Security Lens 분석
    ↓
개인정보 또는 메타데이터 위험 발견
    ↓
사용자에게 경고
    ↓
보호 후 전송 또는 그대로 전송
```

과 같은 흐름입니다.

카카오톡, Gmail과 같은 서비스에 직접 연결하는 방식은
각 서비스가 제공하는 API나 확장 기능에 따라 구현 방법이 달라질 수 있지만,
브라우저 확장 프로그램, API, SDK 또는 기업 내부 시스템 연동 등의 형태로
같은 개념을 적용할 수 있다고 생각합니다.

### 더 깊은 개인정보 분석

현재 MVP에서는 OCR과 규칙 기반 탐지,
이미지 메타데이터 분석과 AI 맥락 분석을 결합했습니다.

앞으로는 단순히 탐지할 수 있는 개인정보 종류를 늘리는 것보다
서로 다른 정보가 함께 있을 때 발생하는 위험을 더 잘 판단하는 쪽으로 발전시키고 싶습니다.

예를 들어 하나의 정보만으로는 위험하지 않더라도
이름, 회사명, 위치, 시간과 같은 정보가 함께 노출되면
개인을 특정하는 데 더 많은 단서가 될 수 있습니다.

Security Lens가 최종적으로 하고 싶은 일은
모든 사진을 위험하다고 판단하는 것이 아니라,

사용자가 무심코 공유하려는 정보 안에
생각하지 못했던 개인정보가 있는지 한 번 더 알려주는 것입니다.
